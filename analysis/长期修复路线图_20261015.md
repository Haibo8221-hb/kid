### 6.2 #10 为何不继续抽取（技术决策，理由留档）

剩余 48 个同名函数中，体量差异显著者（`loadResources` 11420 vs 1807、`renderErrors` 30899 vs 3139、`markdownToHtml` 1299 vs 26725、`loadRoutes` 12949 vs 7200）并不是"复制粘贴后忘了改"，而是**两个孩子的学习内容本就不同**——强行合并需要引入大量分支/配置化，收益（行数下降）低于风险（一个改动同时影响两个孩子的页面）。

因此：**#10 切片 2 停止推进**，改以"已被抽走的 20 个 + 未来新增逻辑一律写进公共层"的方式长期收敛。如需再降重复，正确路径是**把差异数据（resource 表、routes 数据）外置为 JSON 配置**，让两份页面共用同一套渲染代码——这需要先把内容数据结构化，属独立议题，不在本路线图内立项。

### 3.1 P0（阻塞/紧急）

#### #16 部署 rsync 覆盖服务器活数据 ｜ CI/CD · 全版本

- **问题描述**：`deploy.yml:22-36` 的 rsync 带 `--delete`，且未排除 `data/`；本地 31 个 data 文件已入 git。任何一次 `git push` 都会用本地旧数据覆盖服务器活数据（孩子在线新增的错题/计划被静默回滚），并删除仅存在于服务器的文件（`auth_state.json` 登出水印、`llm_config.json`、`uploads/`）。
- **修复目标**：部署只同步**代码**，永不触碰**运行时数据**。
- **依赖**：无前置；但需先确认服务器 `data/` 内容完整（否则首次 exclude 后出问题无本地兜底）。
- **负责人角色**：开发（改 workflow + 验证）；家长（确认是否要把服务器数据反向拉回本地留档）。
- **验收标准**：
  1. `deploy.yml` 的 rsync 参数含 `--exclude='data/' --exclude='logs/'`；
  2. 造一次验证：在服务器 `data/` 新建一个探针文件 → 从本地 push 一次空提交 → 探针文件**仍存在**（未被删）；
  3. 服务器 `data/auth_state.json`、`data/llm_config.json` 在两次部署后仍存在。

#### #1 / #2 / #3 / #4 / #5 / #6 ｜ 已修复，转回归看护

- **处理方式**：不排修复工时，转入**回归看护**（防后续重构击穿）。
- **负责人角色**：开发（把 `tests/verify_p0_fixes.py`、`tests/check_links.py` 挂进 CI，见新增-C）。
- **验收标准**：每次 push，CI 中两个脚本必须全绿；任一失败即阻断部署。
