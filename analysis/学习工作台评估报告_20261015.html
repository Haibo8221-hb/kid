1. 现状梳理

1.1 功能定位

这是一个面向 GCSE / A-Level 阶段学生的个人学习管理控制台（Personal Learning Dashboard），服务两个具体用户：Diya（Year 11，2027 年 5 月 GCSE）与 Jemma（Year 8）。系统英文名 Study Compass · Academic Planner（app.html:495-496），核心使命是把「成绩数据 + 错题 + 备考计划 + AI 对话」收敛到单一页面，避免家长/学生在多个文档间切换。

从代码可确认它同时承担三个角色：

  • 学习数据看板：倒计时、学科成绩卡、雷达图、错题分布、SMC 竞赛进度（app.html:544-750）
  • 规划执行工具：周计划表（7 天 × 3 时段 + Must-Do 行）、任务清单、周复盘向导（app.html:788-838、2401-2463）
  • AI 教练 + 文档门户：SSE 流式对话、学习方法卡片轮播、指向 30+ 独立 HTML/PDF 资料站的导航（app.html:803-820、2602-2655、1750-1876）
注意：这不是一个「课程平台」或「题库系统」，而是一个元数据聚合层 + 个人执行看板。它自己几乎不生产学习内容，而是把散落在 30+ 个静态页面、几十份 PDF、以及后端 JSON 里的信息组织起来。这个定位决定了后面大部分问题的性质。

1.4 核心交互流程

流程 A · 每日主循环（设计意图最清晰的一条）

打开 Dashboard→ 倒计时 + 风险热力图确认今日重点→ 学习方法卡「Try It Now」→ 看错题分布找薄弱学科→ 进 Weekly Plan 排入时段→ 勾选任务环涨 %→ 周日填 Weekly Review

「任务完成率 → 圆环 SVG」这条激励回路实现得最扎实：loadDashboard() 拉 /api/dashboard，算出百分比写入 stroke-dashoffset（1904-1917），并按 0/50/100 三档给出不同鼓励文案。

流程 B · 错题闭环（设计上完整，实现有断裂）

上传作业 PDF/图片→ 后端渲染页面 PNG（pypdfium2 200dpi）→ 5 模型投票 OCR→ LLM 抽取学科/知识点/错题→ 前端预览 + 逐页对照→ 一键写入 Error Book→ 标记 Mastered

这是全系统技术含量最高、最有产品价值的链路（api_server.py:1522-2004）。前端侧 pollUploadStatus() 每 2.5s 轮询、15 分钟超时（app.html:3190-3212），失败可重试 OCR / 重试抽取（3215-3231）。

流程 C · AI 教练（含上下文注入）

sendChatMsg() → /api/chat/stream → 后端 _build_system_prompt() 会读取 chat_prompt.md + Diya_Plan.md 拼入 system prompt（api_server.py:488-514），实现「AI 知道孩子的备考计划」。前端以自定义 markdown 渲染器 markdownToHtml()（2276-2310）处理回复。

2. 优点分析

2.1 内容组织：三个做法明显高于同类个人项目

① 错题卡采用「四段式对照结构」而非简单记录

每条错题固定呈现 5 个层次：原题 → 学生答案（橙）→ 正确答案（绿）→ 弱点诊断（红）→ 如何改进（绿）+ 得分 + 考试来源 + 标签（app.html:2802-2826）。这是符合认知心理学的「对比—诊断—纠正」结构，比多数错题 App 的「截图 + 备注」强得多。Diya 的答案与正确答案左右并排（.ec-answer-section 双栏 Grid，97 行），视觉上直接形成反差。

② 学习方法卡遵循「概念 → 原理 → 步骤 → 立刻练 → 分科应用」五段式

8 张方法卡每张都强制包含 concept / why / steps / practice / apply 五个字段（2604-2655）。其中 apply 字段做到了真正的个性化——不是「多做题」这种空话，而是「Chemistry: Memorise the reactivity series — test yourself tomorrow」这种可直接执行的动作。「Try It Now」段落用「Right now: ...」直接下命令（2608、2615、2622、2629、2635、2641、2647、2653），把阅读转化为行动，这是很成熟的产品设计。

③ 方法卡内容有真实的学术依据与考试情报

主动引用艾宾浩斯遗忘曲线（2606）、明确指出 AQA Paper 1 Q2 中「effect on reader」是三级中权重最高项（3349）、给出 ESAT 与 MAT 的区别（2644）、SMC 2026=2×1013 的年份质因数技巧（3352）、UKMT 官方分数线 Gold 72+/Silver 57+/Bronze 46+（625）。这些是外部知识核对过的信息，不是编造，说明作者（或 AI）做实事的时间投入是真实的。

2.2 视觉层次：设计成熟度明显高于「学生自制页面」水平

  • CSS 变量主题化彻底：:root 定义 12 个变量（app.html:11），setTheme() 支持 5 套配色（blue/purple/pink/green/orange），用户偏好存 localStorage（2915-2921）。这是正规产品做法。
  • 语义化色彩体系一致：--accent（蓝=进行中）、--accent2（绿=已掌握/安全）、--red（风险）、--orange（警告）四个语义色贯穿全站，学科配色在周计划中还有第二套映射（397-403），两套互相不冲突。
  • 倒计时的紧迫度分层做得很好：按剩余天数自动分 4 档（urgent ≤60 天 / warm ≤180 / cool ≤400 / far），对应不同字号与边框色（2594-2597）。60 天内变红加粗到 28px——这是把「信息」升级为「行动信号」的典型手法。
  • 零依赖手绘 SVG 图表：雷达图（2170-2237）、任务完成环（653-658）、SMC 分数趋势折线（2031-2052）全部原生 SVG，配 font-variant-numeric:tabular-nums 防数字跳动。没有引入图表库，208 KB 的文件里没有一个外部依赖。
  • 细节点缀到位：勾选后 opacity:.45 + 删除线（273）、已掌握错题整体降透明度（112）、SMC 分数卡 34px 超大字号（2016）、滚动条收窄到 6px（13）、-webkit-text-fill-color:transparent 渐变标题（34）。这些细节体现的是「有人真的天天在用这个页面」。

2.3 交互逻辑：三处设计值得肯定

  • 全量异步 + localStorage 双写兜底：saveTasks（1380-1394）、loadPlanner（1401-1419）、reviewSubmit（2440-2462）全部是「先试后端，失败落本地并 toast 告知」。后端挂了页面仍可用，这是很好的降级设计。
  • 周回顾做成了向导而非长表单：7 个问题拆成 7 步，进度条 + 上一步/下一步/提交三态切换（2406-2427），符合「单次认知负荷」原则；且校验门槛宽松——只要求「三问中至少填一题」（2452），不强迫写满。
  • 错误可诊断性极强：全局 error 监听把任何 JS 异常弹成红色 toast 并显示行号（1107-1112）；左下角常驻 build 20261014-1745-domfix 版本徽标（1073、1137）；LLM 按钮点击失败时明确提示「很可能是浏览器缓存了旧版，请 Ctrl+Shift+R」（529、1128）。这是被线上问题教育过的产物，很多商业项目都做不到这种自诊断。

3. 不足分析

3.1 【严重 · 功能失效】写操作全部返回 405，且前端不检查

这是本次审计发现的最高优先级缺陷：错题本的「新增」和「删除」功能在生产环境完全不可用。

前端调用后端实际结果
POST /api/errors/diya（app.html:2842）@app.route('/api/errors/<child>', methods=['GET','OPTIONS'])（api_server.py:1324）405，数据未写入
DELETE /api/errors/diya/<id>（app.html:2852）无该路由404，数据未删除
POST /api/wiki/diya（app.html:2547）/api/wiki/<child> 仅 GET/DELETE（api_server.py:724）405，Wiki 无法新增
为何没被发现：saveError() / deleteError() 用 await fetch(...) 但不检查 response.ok，405/404 都不是网络异常，try/catch 捕获不到，于是代码照常执行 toast('Saved')（2845、2852-2853）。这是典型的静默失败（silent failure）——界面在笑，数据在丢。Jemma 侧同一 bug 存在于 jemma.html:916。

连带影响：错题本唯一的写入口是邮件管线 /api/error-save（api_server.py:1275），而该端点写的是另一套字段名（raw/type/solution，1298-1306），前端却读 question/diya_answer/correct_solution/error_type（app.html:2790-2799）——邮件进来的错题在页面上大面积渲染为空。更严重的是平铺分支不生成 id（1298），导致 markMastered('undefined')。

3.2 【严重 · 安全】child 参数未白名单，存在路径穿越

/api/planner(207)、/api/tasks(234)、/api/chat/<child>(249)、chat_stream(538-542)、/api/review(870) 的 child 直接参与文件路径拼接，没有白名单校验。而 error_save(1287)、get_errors(1334)、upload_api(1776) 却都做了校验——同一个代码库里两种标准。传入 ?user=../../xxx 即可把 JSON 写出 data/ 目录。

配套的认证弱点

  • 默认密码硬编码入库：APP_PASSWORD = os.environ.get('APP_PASSWORD', 'haibo2026')（api_server.py:23）。忘配环境变量即用弱口令上线。
  • Cookie 无 secure 标志（96-97、107、126-127），HTTP 链路可明文嗅探。而前端 self-check 里明文出现过公网 IP https://112.74.40.8/app.html（3372），说明确实存在 HTTP 直连场景。
  • 无失败次数限制：登录失败仅靠 time.sleep(0.4) 拖时间（api_server.py:90），无计数锁定、无 IP 封禁——既是爆破面也是自身 DoS 面（每次失败占一个 worker 0.4s）。
  • CORS 兜底为 * 且带 credentials（139-140），当 ALLOWED_ORIGINS 为空时命中；默认域名硬编码 grow-consultant.com（135）。
  • Token 实质永不过期：TTL 30 天 + 剩余 15 天即滚动续期（21-22、125），只要用户每月访问一次就永远有效，且无服务端吊销能力。
  • API Key 明文落盘 data/llm_config.json（api_server.py:414-419、680）。

get_errors 只支持 ?stats=1 聚合模式（api_server.py:1341），没有 limit / 分页。而 Dashboard 已经正确使用了 ?stats=1 来避免全量传输（app.html:1939，注释明确写「avoids shipping the full ~276KB file」）——说明作者意识到这个问题，但只在 dashboard 修了。loadErrorBook()（2741）与 loadSubjectAnalysis()（2861）仍然是两次全量拉取 + innerHTML 全量重绘 113 张卡片，每次切 Tab 都重来一遍。

另一个隐患：_cached_json_read 的缓存写入后不主动失效（api_server.py:183-195），所以 /api/errors 最多返回脏读 15 秒——这解释了为什么「保存后立刻刷新可能看不到」。

3.4 【中 · 内容】学习内容存在大面积重复与自相矛盾

① 两个方法库并存且高度重叠

V2_TIPS_POOL（app.html:2602-2655，8 条，结构化字段）实际只有 loadStudyTips() 一个消费方；STUDY_TIPS_DIYA（3342-3354，8 条，扁平字段）在全文件中没有任何调用点，是完整的死代码。而两者主题高度重合：

主动回忆dm02 Active Recall + Spaced Repetitiontip_02 Active Recall: Close book & explain

② 方法论自身前后不一致（会削弱可信度）

间距重复（spaced repetition）的两套说法：
· dm02（2607）：「明天、3 天、1 周、1 个月」
· dm16（2640）：「今天、然后 2、3、5、7 天后」（自称 2357 法）
· d_s02（3350）：「课后、第二天、第三天、一周后」（自称 2-3-5-7 法）
三套不同的时间表同时出现在同一个页面，学生无从判断哪个为准。

段落法的命名也不一致：dm09/dm14 叫 PETAL（5 步），d_new01 叫 PETZAL（6 步，多一个 Analysis）。同一页面两套缩写。

③ 陈旧数据未清理，与页面自身陈述冲突

废弃常量 TIMER_TARGETS（1277-1283）里 5 个目标日期全部是 2025 年（'2025-11-05' UKMT SMC、'2025-07-01' 暑假），而实际在用的是 COUNTDOWN_ITEMS（2567-2570，2027 年）。TIMER_TARGETS 与 getTimeLeft()（1285-1293）已无调用方——但它就在文件里，任何二次开发者都可能误用这批过期日期。

3.5 【中 · 结构】四份前端并存，且 v2 存在未鉴权的数据暴露

  • 重复规模：规范化比对 app.html 与 jemma.html 得共同行 1,283 行，重复率约 40%；函数名交集 69 个（jemma 侧 86 个函数中 80% 同名）；CSS 变量体系与深色主题几乎照抄（app.html:9-480 / jemma.html:7-324）。v2 内部 diya.html 与 jemma.html 各 253 行、diff 仅 155 行——骨架 100% 复制。
  • v2 完全没有认证：v2 两个 HTML 中 auth/token/401 零匹配，而 v1 有 fetch 拦截 + 探活（app.html:1088-1105）。v2 页面可直连读写全部数据。
  • v2 的 logout 只清本地：v2/diya.html:236 仅 localStorage.clear()，不调 /api/auth/logout，cookie 会话仍有效——点了「退出」其实没退出。
  • v2 配置与实现脱节：config.js:22 声明 tipsPool:'STUDY_TIPS_DIYA' 指向不存在的 tips-data.js，实际靠 HTML 内联兜底；setTheme() 依赖 data-theme 属性高亮，但 HTML 只给了 style+onclick（v2/diya.html:47），主题选中态必然失效。
  • 孤儿模块：tab-subject-analysis（936-939）+ loadSubjectAnalysis()（2857-2884）已完整实现，但侧边栏无入口、switchTab 无触发，是用户永远打不开的死代码。
  • 后端死代码：/api/intel(1083)、/api/resources(1136)、/api/parse-error(1190)、/api/ocr(1499)、/api/activity(1002)、/api/sync(1059)、/api/chat(252) 前端零引用——其中 /api/resources 尤其讽刺：Resources 模块实际用 loadResources() 写死 innerHTML，后端接口完全用不上。

3.6 【中 · 无障碍】几乎为零

实测计数：aria-* 属性 0 处、role= 0 处、alt= 1 处、<label> 18 处。

  • Tab 导航无语义：<div class="tab-panel">（36-37）切换可见性，但无 role="tablist"/"tab"/"tabpanel"、无 aria-selected、无键盘方向键支持、无 URL hash 同步——刷新页面回到 Dashboard，无法分享/收藏某个 Tab。
  • 弹窗无焦点管理：.modal-overlay（325-326）只是 display 切换，无 role="dialog"、无 aria-modal、无焦点陷阱、无 ESC 关闭、无打开时聚焦首个输入框。
  • 表单标签未关联：SMC 表单的 <label>（632-640）没有 for 属性，与 input 无关联；点击标签不聚焦，读屏软件也读不到。
  • 交互元素无语义：任务复选框是 <div class="cb">（274-275，且勾选时内部是空字符串，无对勾字符），theme-dot 是 <span>（515-519），profile-avatar 是 <div>（511）——全部无法用键盘操作，读屏软件只会念出相邻文本。
  • 仅有的 alt 还是误导性的：唯一的 alt="Question image"（2810）对错题图片毫无描述价值。

3.7 【中 · 响应式】仅 2 个断点，移动端基本不可用

全文件仅 @media 出现 2 次（66、67 行），且只作用于 .subject-grid 一个类。侧边栏是 position:fixed;width:220px（17），主内容 margin-left:220px;padding:28px 36px（32）——在 375px 宽的手机上，可用宽度只剩 155px，周历表格（80px + 7×1fr，288）会严重挤压。.task-list 是写死的两列 Grid（269），.dash-grid 两列（241），均无降级。没有侧边栏汉堡按钮、没有底部导航。

唯一有适配意识的是 .sa-grid 与 .rcat-grid 用了 auto-fill/minmax()（118、412）。

3.9 【低 · 并发与健壮性】

  • JSON 写入无锁：atomic_write（150-157）用固定名 path+'.tmp' + os.replace，无 fsync、同名 tmp 在并发下互相覆盖；只有 uploads 索引有锁（1536），tasks/planner/errors/reviews/wiki 的读-改-写全程无锁，会丢更新。
  • 损坏文件被静默清空：safe_load 遇解析失败把文件重命名为 .corrupt 并返回 []（171-179），随后任意一次 POST 就把历史覆写成空——丢数据且无告警。
  • smc_records 有 NameError：api_server.py:1371 引用未定义变量 path（应为 SMC_DATA_FILE），该 JSON 一旦损坏即 500。
  • 日期格式不统一：error_save 用 isoformat() 带时分秒（1294），其余是 YYYY-MM-DD；前端按 new Date() 排序（2786），导致邮件条目与手工条目排序错位、formatRelativeDate 显示异常。
  • 文件句柄泄漏：open(open()) 模式未关闭句柄（383、416、670）。
  • 上传限流在反代后失效：30 次/小时的计数是进程内字典（1780-1787），未启用 ProxyFix，Nginx 后所有用户共用一个桶。
  • OCR 线程池仅 2 workers（1474），单页最坏 5 模型 × 90s 超时（1484），20 页 PDF 排队时间可能极长；200dpi 渲染无内存上限（1623）。
  • 上传限流检查顺序颠倒：f.read() 在大小检查之前执行（1792）。

3.10 【低 · 体验】双孩子切换是「换整页」而非「换上下文」

切换 Jemma 是 <a href="/jemma.html">（538）——整页跳转、丢失当前 Tab 与滚动位置。且全局状态写死 Diya：let currentChild = 'diya'（1135）、loadDashboard() 硬编码 /api/dashboard/diya（1903）、loadErrorBook() 硬编码 /api/errors/diya（2741）、loadReviewHistory() 硬编码 /api/review?user=diya（2491）、localStorage 前缀全部 diya_（diya_notes_、diya_streak、diya_theme、mastered_errors_diya、study_tips_viewed_diya）。这份 3,377 行的「通用」工作台在代码层面其实是 Diya 专用——这正是两份前端重复 1,283 行的根本原因。
